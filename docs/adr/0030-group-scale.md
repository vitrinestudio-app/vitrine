# 0030 – Group scale

- Status: accepted
- Date: 2026-11-13

## Context

Templates built through MCP (`docs/research/2026-11-12-mcp-test-results.md`
§3 P2.1, `docs/research/2026-11-13-mcp-test-results2.md`: trading cards,
tickets, polaroids, feature walls) use groups for "objects with inner
life": a card is a rounded shape, an image, three texts and a badge. Play
variants (other page aspect) need such objects smaller. A group's `at`
(offset) and `rotation` can already be overridden in one place, but a
size change meant overriding `at`, `width`, `height`, `font_size`,
`radius` … of every child – 35 to 200 overrides per canvas, generated by
scripts and not maintainable by hand. Variant `content_scale` scales
devices only.

## Decision

- **Field `scale` on group elements**, a uniform factor, default 1,
  allowed range `0.1..=10` (`model::GROUP_SCALE_RANGE`; checked when the
  element is read and for every patched/overridden element, so a bad
  value in an op or override is rejected). Written only when ≠ 1, between
  `anchor_y` and the kind fields (`canonical` order of `ElementWire`).
  Settable in the base and in **variant overrides** (it is an ordinary
  `ElementPatch` field, so `update_element`, `set_variant_override`,
  `reset_override_field`, inverse ops and history need no new op).
  Language overrides stay text-only (`LANG_OVERRIDE_FIELDS`); groups have
  none.
- **Origin = the group pivot**, the same point rotation uses: the centre
  of the bounding box of the children's reference points (all children,
  visible or not, before the group's own transform) plus the group's
  `pivot` offset. A card keeps its centre when scaled; `pivot: {x: -200}`
  keeps its left edge (the "anchor_x" wish of P2.1). Because the pivot does
  not depend on the scale, changing the scale never moves the origin.
- **Order**: scale around the pivot, rotate around the pivot, then add
  `at`. Uniform scale and rotation around the same point commute, so the
  order only matters for the offset: **`at` is not scaled** (an offset of
  the group in page lu, like today).
- **Resolve, not a render transform.** Groups are flattened in
  `resolve::elements` (`apply_group`); there is no transform matrix in the
  render path, and the renderer, layout reports, validation, overlays and
  edit intents all read the flat `ResolvedElement`. The scale is applied
  there like a transform: the child's world pivot is scaled around the
  group pivot, and size, pivot offset and all kind-specific lengths are
  multiplied – shape `radius` and stroke width, shadow blur/offsets of
  every kind, text frame, font size, `shrink_to`, outline, glow, default
  pivot. Text is therefore **laid out at the scaled size** (sharp glyphs,
  no bitmap scale). Span styles are project-wide, so `ResolvedText::scale`
  carries the factor and `layout::layout_text` scales span outline, glow
  and shadow when laying out. Image `fit: tile` fills scale their tile
  size with `ResolvedElement::scale`.
- `ResolvedElement::scale` (product of all enclosing groups, nested groups
  multiply) is exposed for consumers that convert canvas lu back to model
  lu: `Editor::resize` divides by it (with `content_scale` for devices),
  `Editor::set_pivot` too. Moves need nothing: the Newton solver runs the
  real pipeline. Both new fields are skipped in serialization when 1, so
  resolve snapshots of unscaled scenes are unchanged.
- **Device `content_scale`** stays the variant factor only; the group
  scale is in `ResolvedElement::scale` (the drawn size includes both).
- **Ungroup** of a scaled group (base or any variant override) is refused
  with a clear message: folding a scale into the children would mean
  rewriting every length of every child and its overrides. Reset the scale
  first.

## Consequences

- One override (`scale: 0.85`, maybe `at`) replaces dozens per object.
- Text in a scaled group lays out at `size · k` with the auto-fit step
  (`layout::FIT_STEP`, 0.25 lu) unscaled, so a shrinking text may pick a
  size a fraction of a step different from the exact scaled one; line
  breaks are otherwise identical.
- Moving an element into or out of a scaled group (`Editor::arrange`)
  keeps its position, not its drawn size (it takes the new group's scale).
- Not scaled: `clip: page` rectangles (they are page geometry), canvas
  backgrounds, the group's own `at`. A page background inside a scaled
  group is scaled like any child (rarely useful).
- The GUI inspector shows "Scale" (percent) for groups, with the pivot row
  as its origin; canvas handles do not resize groups (unchanged).
