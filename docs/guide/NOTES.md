## 1. Getting started
- CLI quick start: `vitrine new <dir> [--template phone|minimal] [--lang en --lang de]` → `vitrine validate` → `vitrine export`.
- GUI: `vitrine-gui [project-dir]` opens a project directly; otherwise start screen (new / open / recent).
- Project = folder: `project.yaml`, `i18n/<lang>.yaml`, `screenshots/<lang>/<variant>/<key>.png`, `assets/`, `fonts/`, `export/` and `.cache/` (both gitignored).
- Every edit is saved immediately (no "Save"); external edits (e.g. by an AI assistant via MCP, a text editor, git checkout) are reloaded live.

## 2. Concepts
- Page width is always 1000 lu (logical units); height follows the aspect. Sizes in lu → export resolution independent.
- Home page: each element's position is relative to its page; elements may reach into neighbouring pages (a phone spanning two screenshots exists once).
- Gaps: stores show screenshots with gaps; Vitrine Studio builds the canvas with those gaps so continuous elements line up in the store; content inside a gap is not exported. Gap values per gallery profile; app-store web values measured from apps.apple.com CSS, native store apps still placeholders.
- Anchors (`top|bottom|center|stretch`) adapt one layout to other aspect ratios (e.g. iPhone 1:2.17 vs Play 1:2).
- Grouping `group: 2`: two portrait pages → one landscape image (iPad landscape from the phone canvas).
- Variants: per-format overrides (position, size, rotation…) while content stays shared. Inspector marks overrides purple.
- Language overrides: per-language text tweaks (font size, box, style, fit, effects); marked teal in the inspector; `de-AT` inherits `de`.
- Regional languages (`fr-CA`, `de-AT`, `pt-BR`): fall back automatically to their prefix language (`fr-CA → fr → default`); translate only the keys that differ (example: fr-CA has 2 Québec texts, "jardin communautaire", "cellulaire"). No `languages.fallback` entry needed for prefixes; use it only for non-prefix chains.
- Fallback order: a language's own chain first (prefix, then its `languages.fallback` entry, e.g. `fr → en`), the default language only last. Assets panel → Screenshots shows per language which images come from where ("From en (fallback)", "From de (default language)", per key and variant, resolved like the renderer) and on the source language "fallback for fr, nl"; hover a language for its full chain.
- Fallback severities: text from the default language = warning "not translated" (fails `validate --strict`); text from a prefix/configured fallback = info; screenshot from any fallback = info. A partial screenshot set per language is fine (missing ones come from the fallback chain).
- Rotation sign: positive = clockwise (CSS convention).

## 3. How-to notes

### Canvases, targets and variants in the GUI (2026-11-10)
- One place: menu → "Canvases & targets…" ("Leinwände & Ausgabeziele …", also the targets button next to the target picker). Left: every canvas with its targets; click a canvas header for the canvas pane, a target for its form.
- New canvas ("+ New canvas"): start with *Empty* (one light background), *Headline + device* (per page a text with placeholder "Your headline" in the default language under key `<canvas>.<page>.title`, plus a device whose screenshot key is the page id) or *Copy of a canvas*. Page format = a store preset size (or a custom aspect); "Also add this target" creates the matching target in the same undo step (a canvas without targets cannot be shown or exported). Page count default 3 for portrait pages, 1 for landscape.
- Copy of a canvas = KONZEPT "duplicate canvas": pages, backgrounds, elements (new unique ids, e.g. `title-plan-2`; element ids are unique across the project), variants with re-keyed overrides. Options: also copy its targets (ids `<target>-<new canvas>`), own copies of the texts (new keys `<new canvas>.<key>` with all translations; off = both canvases share the translations).
- Canvas pane: rename (targets follow), Duplicate…, Remove (confirmation lists elements, variants and the targets that go with it; refused for the last canvas; one undo step), "Show in editor", targets of the canvas + "Add target", variants.
- Variants: "New variant…" dialog – name, based on the base layout (empty) or a copy of another variant (overrides + content scale), content scale, "Shown by" targets (they switch to the new variant in the same undo step). Removing a variant that targets show detaches them (they fall back to the base layout) after a confirmation. A target picks its variant in its form (Variant select, with "+ New variant…"); the top-bar Variant picker only changes what you look at/edit.
- Top-bar pickers (canvas, target, language, variant) end with "+ …" entries: new canvas → canvases & targets dialog (new canvas form), add target → dialog in add mode for the current canvas, add language → project settings → Languages with the input focused, new variant → New variant dialog (afterwards the editor shows the new variant, so edits become its overrides).
- Also reachable: Canvases sidebar tab ("New canvas…", "Manage…", double-click a canvas) and the inspector's canvas settings (variants: duplicate, remove, "New variant…", "Manage…").
- Undo/redo of canvas/target changes keeps the view valid (unknown canvas/target/variant falls back to the first one).

### Store sizes (verified in App Store Connect web app, 2026-11-10)
- Required iPhone set: "iPhone with Dynamic Island (medium display)" = 6.3" = 1206×2622 → `APP_IPHONE_61`. All other iPhone sizes optional (scaled by Apple).
- 6.9" 1320×2868 / 1290×2796 → `APP_IPHONE_67` (no `_69` type exists).
- 1260×2736 and 1512×2316 are listed on Apple's help page but rejected by the ASC uploader → Vitrine Studio does not offer them.
- iPad 13" 2064×2752 / 2048×2732 → `APP_IPAD_PRO_3GEN_129` (required if the app runs on iPad).
- Mac: 16:10 only (1280×800, 1440×900, 2560×1600, 2880×1800).
- Google Play: long side ≤ 2× short side, 320–3840 px, 2–8 per device type, ≥ 4 at ≥ 1080 px for recommendations.
- iPhone Duo (2026-11-10): outer 1398×2034 / 2034×1398, inner 2007×2853 / 2853×2007 (larger than the 1878×2670 panel, same aspect). Presets `ios-iphone-duo-outer` / `-inner`; upload only through the App Asset Library (display class `IPHONE_DUO`, not in the screenshot-set API). Required from April 2027 for apps built with the iOS 27.1 SDK.
- Apple Watch: ONE watch size for all localizations is enough: `watch-ultra` 422×514 / 410×502, `watch-series` 416×496 (Series 10+), legacy `watch-series-7` 396×484, `watch-series-4` 368×448, `watch-series-3` 312×390.
- Wear OS (`play-wear`): 1:1, 384–3840 px, app UI only (no frames, texts, backgrounds) → info `store_decorations` when a non-screenshot-only target has any.

### Creative assets (App Store header / search results, iOS 27+)
- Optional, one image per localization, rendered like a banner from a region of a canvas: `ios-header` (21:9, 3840×1646 exact), `ios-search-results` (3:2, any size 1920×1280 … 3840×2560; default region pages 1–3, which is about 3:2 for portrait pages), `ios-creative-universal` (16:9 PNG 5244×2950, serves both placements; default region pages 1–4).
- Store slot `{apple: {display_type: PRODUCT_PAGE_HEADER_ASSET|APP_STORE_SEARCH_RESULTS_ASSET, placement: header|search_results|universal}}`; uploaded only through the App Asset Library, never into a screenshot set.
- Rules (Apple): short phrase that enhances the visual, localized; no prices, URLs, ©, unverifiable awards, other platforms, Apple awards; suitable for 4+.
- Safe area: Apple defines it only in its design templates (Figma/Photoshop/Pixelmator/Sketch), no numbers published → presets have none. Set `safe_area: {top, right, bottom, left}` (insets in % of the image) on the target (Targets dialog → Safe area): the canvas shows it as a dashed rectangle per output image and validation warns `text_outside_safe_area`.

### Watch and Wear OS: screenshot only
- Target option `screenshot_only: true` (Targets dialog → "Screenshot only"; default for all watch presets and `play-wear`): every page exports the screenshot of its largest device alone, filling the image (square corners, no frame, background, text, shadow or rotation). Use the target's screenshot variant (`watch`, `wear`) so the watch captures are picked by key.
- A page without a device stays empty (warning `screenshot_only_empty`).
- Parametric watch frames `watch-ultra` (rugged, crown guard, action button) and `watch` (rounded, crown + side button) exist for marketing layouts; Apple draws its own watch mask in the store, so exports stay unframed.

### Foldables (iPhone Duo)
- Two catalog models, one per fold state: `iphone-duo` (open, inner display, landscape natural: the hinge is vertical; portrait = rotated, hinge horizontal) and `iphone-duo-folded` (closed, outer display, portrait natural, hinge spine on the left, punch-hole camera top right – position approximated).
- Device field `fold: open|folded` (inspector → Fold) switches between them; it also works after `device_map` (map a phone to `iphone-duo` and fold it per element).
- Drawing: faint crease line over the inner display and hinge seams in the bezel; the inner camera is under the display and not drawn.

### Screenshots import
- Supports Vitrine Studio folder layout, fastlane snapshot output (`de-DE/iPhone 17 Pro Max-01_home.png`), flat folders.
- Locale `de-DE` → `de` automatically; device name → variant by mapping or pixel size; `01_home` → key `home`.
- `_framed.png` (frameit) and `screenshots.html` are skipped.
- A whole `fastlane/` folder can be picked: `screenshots/` = snapshot output, `metadata/android/<locale>/images/<type>Screenshots/` = screengrab output (phone → `android-phone`, 7"/10" → `android-tablet`, wear → `wear`, tv by pixel size; `--device-map tenInchScreenshots=…` overrides; the `_<millis>` timestamp is dropped). Picking `metadata/android` or `metadata` works too.
- snapshot names like `iPhone 15 Pro Max-01Home.png` → key `home` (number glued to a capitalised word is dropped; `3D`, `2fa` stay).
- Skipped with a reason: `Framefile.json`, `title.strings`, `keyword.strings`, the background images a `Framefile.json` names, `iMessage/` and `appleTV/` folders, deliver metadata (`metadata/<locale>/*.txt`), Play store graphics (`images/featureGraphic.png`, `icon`, `tvBanner`, `promoGraphic`).
- Locale folders also match through the store locale map: `iw-IL` → `he`, `zh-Hans`, `no` (project `store.locales` or the defaults).
- Mapping can be saved to `project.yaml` (`import.fastlane`) so re-imports run unattended.
- CLI: `vitrine import screenshots <dir> [--dry-run] [--device-map "NAME=VARIANT"] [--save-mapping]`.

### Translating
- Markup: `**bold**`, `_italic_`, `[style]…[/]`, `\n`, soft hyphen `\-`.
- Soft hyphen: invisible unless the line breaks there; then a visible hyphen.
- Emergency break (word split without hyphen) is reported as a warning.
- Automatic hyphenation: opt-in (`hyphenate: true`), only kicks in when text doesn't fit even at `shrink_to`. Bundled languages: en-us, en-gb, de (1996), fr, es, nl, it, da, pt, nb/no, fi. Swedish missing (pattern licence LPPL 1.2 only, GPL-incompatible; ADR 0022).
- Exchange: CSV (Excel variants with BOM/`;` detected) and XLIFF 1.2/2.0; markup becomes protected inline tags so CAT tools don't break it; import shows a dry-run diff and post-import overflow check; one undo step.
- CSV context column gives element/page/style and an approximate max length.
- XLIFF/CSV export writes one file per non-default language; a sparse regional language (fr-CA) gets all keys it lacks with `--missing-only`.
- French typography: put a no-break space (U+00A0) before `:` `;` `?` `!` and inside « guillemets »; also to keep words together on one line ("le bon\u00a0moment"). Line breaking respects it.
- YAML: a translation containing `: ` (colon + space) or starting with `"`, `[`, `*` must be quoted (`"…"`); the GUI/strings import write correct YAML automatically.
- Hyphenation tip: auto-fit shrinks first and hyphenates only at `shrink_to`. If a long compound makes a headline shrink too much in one language, raise `shrink_to` for that language with a language override (`langs: {de: {fit: {shrink_to: 78, max_lines: 2}}}`) so hyphenation kicks in earlier; widen the box (`box`) if the break lands at an ugly syllable (it takes the last pattern point that fits: "Mischkul-turpartner" vs "Mischkultur-partner"). Soft hyphen `\-` forces the exact point. Example: `title-companions` in the example project.
- Validation info `hyphenated` lists every text that was hyphenated automatically per target × language – check those renders.

### Apple device frames (Apple Design Resources "Product Bezels")
- User downloads the bezels themselves from developer.apple.com/design/resources; Vitrine Studio never ships or uploads them (Apple licence; License.rtf in the package).
- The DMGs contain a licence agreement: **open the DMG in Finder, accept the licence, then import the mounted volume** (`/Volumes/Bezel-iPhone-18`). Direct DMG import fails with "attach canceled".
- Package contents: PNGs per model/colour/orientation (`iPhone 18 Pro Max - Black - Portrait.png`), Photoshop files (ignored), License.rtf.
- iPhone 18 package (verified 2026-11-10): models Pro and Pro Max; colours Black, Burgundy, Glacier, Silver; screen exactly 1320×2868 (Pro Max) / 1206×2622 (Pro).
- Frames are stored app-wide (app data dir), never in the project; projects only say `frame: imported:apple`. Missing on another machine → parametric frame + info.
- CLI: `vitrine frames import <path> [--dry-run -v]`, `frames list`, `frames remove`.
- Import report (2026-11-11): three kinds of not-imported PNGs, kept apart – **skipped on purpose** (a `skip` rule of the source, with its reason, e.g. `skipped  iPhone Duo - Night Sky - Outer Open.png  (on purpose: marketing composite …, not a single device view)`; GUI badge "Skipped on purpose", no assignment controls, own count in the summary), **ignored (your choice)** (your saved mapping), **unknown / unmatched** (no rule matched; assign by hand). Only the last one counts as "unmatched".
- iPhone Duo package `Bezel-iPhone-Duo.dmg` (verified 2026-11-10): `iPhone Duo - <Night Sky|Star White> - <Inner Open|Outer Closed> <Portrait|Landscape>.png` → `iphone-duo` (open, screen 2007×2853) / `iphone-duo-folded` (closed, 1398×2034). `… - Outer Open.png` (back + outer display, open flat) is skipped on purpose as a marketing composite (rule files support `skip:` patterns with a reason).
- Apple Watch Ultra package `Bezel-Apple-Watch-Ultra-4-2026.dmg` (verified 2026-11-10): `AW Ultra 4 - <Case> + <Band>.png` (620×940, case with band, screen 422×514) → `watch-ultra`; the colour key is case + band (`natural-trail-loop-sand`), so all six combinations are installed side by side. `AW Series <n> - …` → `watch` is a guess (unverified).
- Both Pro and Pro Max bezels are kept; the bezel is picked per target size (else screenshot size), or pinned per device ("Bezel" in the inspector: "Auto · 18 Pro Max").
- Use them for the whole project: Project settings → General → Frame style → "Apple (imported)" (`styles.frame: imported:apple`); a hint shows when no Apple frames are installed. Per device: inspector → Frame.
- Colours come from the package (Black, Burgundy, Glacier, Silver for iPhone 18), not from Vitrine Studio's palette. With an Apple frame the inspector shows only the installed colours, as swatches in the real housing colour (measured from each bezel at import: outer metal rim, black glass border excluded; stored as `swatch` in the store's `index.yaml`, filled in for older imports the first time the frame list is shown).
- Switching the frame source (device or project default) changes the colour too, in the same undo step: the closest colour of the new source by housing colour (Black titanium → Black, Natural titanium → Silver; Burgundy → Black titanium back). Round trips can change the colour (White titanium → Silver → Natural titanium).
- A colour that is not installed (e.g. project from another machine) → the default/first installed colour is drawn, info `imported_color_fallback`. No Apple frame installed at all → built-in detailed frame with the default colour, info `imported_frame_missing`.

### Text effects
- Outline (stroke), glow, shadow on text styles, span styles and elements. Precedence span > element > style. Disable inherited: `width: 0`, `opacity: 0`, `shadow: none`. Sizes in lu (don't shrink with auto-fit).

### Images
- PNG/JPEG/SVG. Shadows of transparent images follow the alpha (like CSS drop-shadow). Text inside SVGs is not rendered yet.

### Colours (colour management, Phase 6.1, ADR 0021)
- Vitrine Studio works in sRGB. Colours you type (`#RRGGBB`) are sRGB.
- Screenshots, images and imported Apple bezels with a colour profile are converted to sRGB when loaded: Display P3 (iPhone/Mac screenshots), Adobe RGB, gray profiles … Read from PNG `iCCP`/`cICP`/`sRGB` and JPEG ICC. Same result in the editor, export, upload and MCP previews.
- No profile = sRGB. PNG `gAMA`/`cHRM` alone are ignored.
- P3 colours outside sRGB are clipped to the nearest sRGB edge (very saturated reds/greens look slightly less vivid than on a P3 display – same as in any sRGB export).
- Validation info `color_profile_unsupported` (per screenshot file): profile unreadable, CMYK JPEG, HDR (PQ/HLG) PNG or unknown cICP → the image is drawn as if it were sRGB. Fix: re-save as sRGB or Display P3 PNG.
- 16-bit PNGs are converted at full precision, then reduced to 8 bit.
- Exports: PNG with `sRGB` chunk, JPEG untagged (= sRGB). No Display P3 output (yet).
- Bezel colour swatches measured before this change came from unconverted pixels (tiny difference).

### Export
- Files: `export/<target>/<lang>/<nn>_<page-id>.png`, grouped `<nn>_<id1>+<id2>`, `banner.png`, `_gallery.png`.
- `index.html` in the export folder (on by default; CLI `--no-html`, GUI "Overview page", MCP `html: false`): every exported image (no gallery previews) by language → target in page order, file name, pixel size, file size; click to enlarge, ←/→ to step, Esc to close. Self-contained (opens from the file system, no internet), light/dark. Lists all current files of the folder, also from earlier exports of other targets.
- Re-export removes images of the same targets × languages it no longer produces (fewer or renamed pages) – only files the export wrote earlier (listed in `.vitrine-export.json`), never other files in the folder.
- fastlane layout: `vitrine export --layout fastlane [--out <app>/fastlane]` (GUI: Layout → fastlane; MCP `layout: "fastlane"`), default folder `export/fastlane/`:
  - App Store targets → `screenshots/<asc-locale>/<nn>_<target>.png` (deliver; iMessage sets in `screenshots/iMessage/<locale>/`); Google Play → `metadata/android/<play-locale>/images/<type>/<nn>_<play-locale>.png` (supply), feature graphic → `images/featureGraphic.png`.
  - Store locales: project `store.locales` or the defaults (`de` → `de-DE`, `he` → Play `iw-IL`). `nn` keeps page order in deliver's natural and supply's alphabetical sort.
  - Left out with a note: targets without a store slot (web, blog), App Store creative assets (header/search results), sizes deliver rejects (deliver would abort the whole upload), languages without a store locale. No gallery previews (deliver would try to upload them).
  - deliver detects the set from the pixel size, so two targets of one size class (e.g. 1320×2868 and 1290×2796 both = APP_IPHONE_67) in one locale folder are a **conflict**: the first wins, the other is not written (error). Same for two targets with one Play image type. More than 10 (Apple) / 8 (Play) images in a set → warning.
  - 2048×2732 iPad targets with slot `APP_IPAD_PRO_129` get `_app_ipad_pro_129` in the file name (deliver's 2nd-gen marker).
  - Warns when the deliver folder holds frameit `*_framed.png` files: deliver then uploads only those.
- Migrating from fastlane frameit:
  - `vitrine import screenshots fastlane/` (keeps snapshot/screengrab capture in place; frameit files are ignored).
  - Design the layout once in Vitrine Studio (texts from `title.strings`/`keyword.strings` go into the strings, per language).
  - `vitrine export --layout fastlane --out fastlane` and drop `frameit` from the Fastfile; `deliver`/`supply` (`upload_to_app_store` / `upload_to_play_store`) upload the folders unchanged. Delete old `*_framed.png` files first.
  - Or skip deliver/supply for screenshots and use Vitrine Studio's own upload (`vitrine upload plan`).
  - Conventions and sources: `docs/research/2026-11-10-fastlane-conventions.md`.
- Always opaque (no alpha), sRGB. Incremental: unchanged images are skipped (`--force` to re-render).

### AI assistants / MCP (Phase 4)
- Vitrine Studio is a plain MCP server: any MCP-capable client works. App settings → "AI assistants (MCP)": generic part first (switch, status, fixed port, start on demand, "Other MCP clients" with the stdio command and the HTTP URL + bearer header), then the client-specific setup ("Claude Desktop", "Claude Code").
- Generic config (any client): stdio server `vitrine-studio` with command `<abs path>/vitrine`, args `["mcp"]` (recommended, always reaches the running app); or Streamable HTTP `http://127.0.0.1:<port>/mcp` with header `Authorization: Bearer <token>` (both from the settings, valid until the app restarts).
- Claude Desktop: App settings → "AI assistants (MCP)" → "Add to Claude Desktop…" (shows file + entry, asks, backup `claude_desktop_config.json.bak-<UTC timestamp>`) → restart Claude Desktop. Entry: `mcpServers.vitrine-studio = {command: "<abs path>/vitrine", args: ["mcp"]}`. Config file: macOS `~/Library/Application Support/Claude/claude_desktop_config.json`, Windows `%APPDATA%\Claude\claude_desktop_config.json`, Linux `~/.config/Claude/claude_desktop_config.json`. Already present → "Already set up"; CLI moved → updated in place; broken JSON → nothing written.
- The app hosts the MCP endpoint (setting "Allow AI assistants to connect via MCP", default on, switches live): Streamable HTTP on `127.0.0.1:<random port>/mcp` (optional fixed port setting), bearer token (new per start), loopback Host/Origin only. Discovery file `<app data>/mcp.json` (port, token, pid; 0600; removed on exit).
- `vitrine mcp` (stdio, what Claude Desktop and other stdio clients start): running app found → forwards to it (the assistant edits what you see); none → starts the app (setting "Start on demand", default on; waits ≤ 20 s); else / `--headless` → own session on `--project` (default `.`, if it holds a `project.yaml`), the assistant uses `project_open` / `project_create`.
- Claude Code: `claude mcp add vitrine-studio -- <path>/vitrine mcp` (recommended) or the HTTP command with port + token from the settings (valid until the app restarts). Headless/CI: `vitrine mcp --headless --project <dir>`.
- Live aids: top-bar sparkle indicator (grey = off, "MCP" = ready, orange with the client's name = connected; tooltip), click → "Assistant activity" (time, label, click selects, undo for the latest step); an assistant's changes are outlined on the canvas for 1.5 s and shown as small toasts "<client name>: …" (click selects). Projects an assistant opens/creates open in the app (start screen → editor).
- In the app, tools default to what you look at: omitted `target` = the current target (if it shows the canvas), omitted `lang` = the current language. `view_get` / `selection_get` read the view and selection ("make this bigger").
- Client display names (from `clientInfo`): `claude-ai` = Claude Desktop, `claude-code` = Claude Code, others their `title`, else the prettified `name` (`my-client` → "My Client"), else "Assistant"; a client counts as connected while it has a session or was active in the last 5 min.
- Every change by an assistant is one undo step labelled `<client name>: …` (e.g. `Claude Desktop: Move title`) in the shared history (undo in the app or with `history_undo` / `history_redo`). Event actor: `{kind: "assistant", client, name}` (was `kind: "claude"` before 2026-11-10; still accepted).
- The assistant sees the result: `render_preview` returns a PNG (view `image` = one exported image, `canvas` = whole canvas with hatched gaps, `gallery` = store gallery; `max_edge` default 1200) plus the errors/warnings of that target × language.
- External edits (text editor, git checkout, the GUI) are picked up before every tool call; a `project.yaml` that does not load gives error `load` and nothing is written.
- No network; files are written only inside the project folder and to paths given explicitly (`export.out_dir`, `strings_export.path`). Installed device frames are read-only over MCP (`frames_list`).
- Coordinates over MCP: lu, page 1000 lu wide; `element_move` x/y = element centre relative to the top-left of a page (default: home page), or `dx/dy`. Rotation degrees, positive = clockwise.
- Edit scope: `base` (default, all targets/languages), `variant` (format override, e.g. iPad landscape), `lang` (per-language text override).
- Resetting overrides: in scope `variant`/`lang` a field set to `null` is **removed from the override** (back to the base value; overrides never store `null`). `element_reset_override {id|ids, scope: variant|lang, variant?, lang?, fields?}` removes fields or the whole override. A hand-written `null` inside an override in `project.yaml` is ignored, reported as info `override_null` and dropped on the next save. In scope `base`, `null` still resets the field to its default.
- One undo step for several changes: `element_update {updates: [{id|ids, patch, scope?, lang?, variant?, strings?}, …]}` (e.g. font size for de and fr at once); ids may come from several canvases (`element_update`, `element_remove`, `element_reorder`, `element_rotate`, `element_move` with dx/dy) – each canvas is edited on the view's target if it shows that canvas, else on the first target showing it. `apply_ops` `update_element` writes the base only; overrides via `set_lang_override`, `reset_lang_override_field`, `set_variant_override`, `reset_override_field`.
- Field reference without resources: `docs_get {topic}` (overview, elements, ops, project, markup, targets, scopes). Claude Desktop does not let the model read MCP resources by itself (the user attaches them), so the docs are a tool too.
- `assets_import`: kind `screenshot` | `asset` (any image for image elements and image fills → `assets/`, alias `image`) | `font`. Many single files with their own key/name in one call: `files: [{path, kind?, key?, name?, lang?, variant?}]` with per-file results and `dry_run`. Whole folders (fastlane, language folders): `screenshots_import`.
- Canvases over MCP: `canvas_add` (empty or `start: "starter"`, optional `target_preset` → canvas + target in one undo step; `aspect` optional with a preset), `canvas_duplicate {canvas, id?, copy_targets?, copy_strings?}`, `canvas_rename`, `canvas_remove` (with its targets). `canvas_variant` add takes `from` (copy another variant) and `targets` (they show it); remove detaches the targets showing it instead of refusing.

### Store accounts & store mapping (Phase 5.1, ADR 0016)
- Accounts are app-wide (App settings → Stores), not in the project: a project folder can be shared via Git, keys stay on the machine.
- Where keys are stored: the system keychain (macOS Keychain, Windows Credential Manager, Linux Secret Service), service `app.vitrinestudio`, account `<account id>/apple` or `<account id>/google`. `settings.yaml` only lists id, label, Apple issuer id + key id, Google client email + project id.
- Import Apple: App Store Connect → Users and Access → Integrations → App Store Connect API → generate a team key, download `AuthKey_<KEYID>.p8` (only once possible). In Vitrine Studio: "Add App Store Connect key…", pick the file, enter the issuer id (shown above the key list); the key id comes from the file name. Role needed for screenshots: App Manager (Admin works too) – to confirm in the real upload test (5.6).
- Import Google: Google Cloud console → IAM → Service accounts → create one, Keys → Add key → JSON. Play Console → Users and permissions → invite the service account e-mail, app permission to edit the store listing ("Store presence"); the Google Play Android Developer API must be enabled in the Cloud project. In Vitrine Studio: "Add Google service account…", pick the JSON. Exact permission names to confirm in 5.6.
- Import checks the file (Apple: PEM EC P-256 private key; Google: `type: service_account`, `client_email`, `private_key`) and never shows key content in messages.
- Remove account = deletes the keychain entry too (with confirmation). Projects keep the reference and show "account not found".
- Test (app settings → Stores → Test): read-only. Apple: signs a token and lists apps → "key accepted, N apps visible (first: …)"; 0 apps = check the key's role/app access. Google: only gets an access token from Google → shows the service account e-mail; Play Console permissions are only checked at upload. Errors: "key rejected" (wrong issuer/key id, revoked or deleted key, wrong system clock), "no access" (Apple role too low), "cannot reach … – offline?", server problem / rate limit / timeout → try again later. CLI/MCP do not test connections.
- Project settings → Stores: App Store (account, Apple ID = numeric app id, bundle id, platform iOS/macOS), Google Play (account, package name), store languages per project language.
- App picker (App Store): with an account chosen, "Choose app…" lists every app the key can see (name – bundle id; SKU and primary language shown for the chosen one) and fills Apple ID + bundle id; ⟳ reloads (the list is kept for the app session). Typing the ids by hand still works. The platform is not suggested (App Store Connect's app list has no platform).
- Google Play cannot list the apps of a service account (no such API call) → type the package name (shown under the app name in Play Console). "Check" asks Play whether the package exists and the service account may edit it: it opens a temporary draft edit, reads the app details (default language + listing title) and deletes the edit again – never committed, nothing changes. Only runs when you click it. Errors: "Google Play does not know this package, or the service account has no access" (404), "no permission for this app" (403, invite the service account in Play Console).
- Help in the app: App settings → Stores (and the import dialog) → "How do I get an App Store Connect key?" / "How do I get a Google Play service account?" – numbered steps (summary of "Store upload – setup" below) and buttons that open App Store Connect API keys, Apple's guide, the Cloud console (enable the API, service accounts), Play Console and Google's guide in the browser (only these fixed links can be opened). Stated in the UI but not yet verified with a real account (to be confirmed in 5.6): role App Manager is enough; Play permissions "View app information (read-only)" + "Manage store presence"; new Play permissions can take up to 24 h. Individual Apple keys: the UI says they are not supported yet (the import needs an Issuer ID).
- `project.yaml`: `store: {apple: {account, app_id, bundle_id, platform, upload_flow}, google: {account, package_name}, locales: {apple: {en: en-GB}, google: {…}}}`; only stores listed there are uploaded (`upload_flow`: see "App Store upload method").
- Locale mapping: explicit entry → project language if it is a store code (`fr-CA`, `pt-BR`) → built-in default for the tag → default for the base language (`de-AT` → `de-DE`). Google uses `iw-IL` for Hebrew, `zh-CN`/`zh-TW`, `es-419`; Apple uses `zh-Hans`/`zh-Hant`, `he`, `no`, plain `ja`, `ko`, `it`. Lists: `crates/core/data/store-locales.yaml` (checked 2026-11-10).
- Validation (only for mapped stores): language without store locale, two languages on the same store locale (e.g. `de` + `de-AT`), unknown code, store without any target slot, two targets on the same display type for the same language.
- MCP: `store_config_get` is read-only (no secrets); assistants cannot import keys or change the mapping (`apply_ops` refuses `set_store`).
- Testing without the real keychain: `VITRINE_KEYRING=mock` (in-memory), `VITRINE_KEYRING_SERVICE=<test name>`; the dev bridge uses the in-memory keychain unless `--system-keychain`.

### Store upload – setup (Phase 5; docs checked 2026-11-10, details in ADR 0017)
- Apple, App Store Connect API **team key**: App Store Connect → Users and Access → **Integrations** tab → "App Store Connect API" (left column) → Team Keys → "Generate API Key" (or +) → name + **Access** role → Generate. Needs an **Admin** account to create team keys. Role for screenshot upload: **App Manager** (edits App Store details; Admin works too but is broader than needed).
- The private key `.p8` can be **downloaded only once** (Apple keeps no copy). Note the **Key ID** (in the key list) and the **Issuer ID** (shown above the key list). Lost/leaked → revoke the key in the same place.
- Individual keys (user profile → Individual API Key) also work: no Issuer ID, access = that user's roles; a team Admin must grant "Generate Individual API Keys".
- Apple only lets you change screenshots on a version in an editable state (e.g. "Prepare for Submission", rejected); otherwise create a new version in App Store Connect first. Upload error then: "no editable App Store version".
- Apple processes each uploaded screenshot (seconds to minutes); wrong dimensions show up as a processing error per image.
- Apple's API limit: about 3500 requests/hour per key (rolling); Vitrine Studio waits and retries on rate limits.
- Note: Apple deprecated the screenshot-set API (API 4.5.1) in favour of the "App Asset Library"; it still works, Vitrine Studio will follow (ADR 0017).
- Google Play, service account: Google Cloud Console → create/select a project → enable "**Google Play Android Developer API**" → IAM & Admin → Service Accounts → "Create service account" → Keys → Add key → JSON (download). Linking the Play developer account to the Cloud project is no longer needed.
- Play Console → **Users and permissions** → "Invite new users" → service account e-mail → app permissions: **"Manage store presence"** (store listing text and images) + "View app information (read-only)" for the app(s) → Invite user.
- Google image upload: PNG/JPEG, max 15 MB per image; images appear in upload order. Changes go live only when the edit is committed (one commit per upload run).
- Secrets: both keys are imported once in the app settings and stored in the system keychain; Vitrine Studio never writes them to the project or logs (5.1).

### Store upload – how to upload (Phase 5.2/5.5, ADR 0018)
- Always **plan → confirm → upload**. Nothing goes to a store without a plan and an explicit confirmation (also not from an AI assistant).
- Setup checklist first: the Upload dialog lists what is missing, in order, each with a button: 1. App settings → Stores (no App Store Connect key / Google service account on this computer, or the project's account is not set up here) → "Open app settings"; 2. Project settings → Stores (project not linked, no account or app chosen, store-language conflicts; languages without store language are a warning) → "Open project settings"; 3. Targets (no target with a store slot, two targets on the same slot) → "Open targets". The list refreshes when the opened dialog is closed. Codes: `no_account`, `account_missing_for_project`, `project_not_mapped`, `store_locale_unknown`, `store_locale_conflict`, `no_store_locale`, `no_store_slots`, `store_slot_conflict` (`upload_readiness`, also `readiness` in every plan; MCP `upload_plan` prints them as numbered hints).
- GUI: menu → "Upload to stores…" (or "Upload…" in the export dialog). One tab per store the project is mapped to. The plan table lists target · language · store locale · action (Upload / Replace / Unchanged / Skipped / Blocked) · images · problems. "Confirm & upload" asks once more, then shows progress per set; "Cancel upload" stops it; "Upload log" lists past runs.
- CLI: `vitrine upload plan [--store apple|google] [--target ID]… [--lang L]… [--remote] [--force] [--format json]` prints the plan and a confirm token; `vitrine upload execute --confirm <token> [--yes] [--changes-not-sent-for-review]` uploads with progress on stderr (asks y/N in a terminal; `--yes` for scripts); `vitrine upload log [--last] [--events]`. `--app-dir` / `VITRINE_APP_DIR` selects the settings with the store accounts. Exit codes: plan 1 = blocked; execute 0 = completed, 1 = partial/failed/cancelled, 2 = refused (token, keys).
- What the plan does: renders the store targets into `<project>/.cache/upload/images` (incremental, like export), puts the images in store order, hashes them, and compares with the last successful upload in the log. Same images → "Unchanged" (skipped). `--force` / "Upload unchanged sets too" uploads anyway.
- "Check store state" / `--remote`: also asks the store (needs network + the account key): Apple – app, editable version (else blocked: "no editable App Store version"), whether the localization and screenshot set exist, the checksums of the screenshots there; Google – opens a temporary edit (deleted again, nothing changes), compares the listing images' SHA-256. A set the store already holds identically shows "Unchanged".
- Blocked = cannot upload: validation errors of that target/language (missing screenshots, wrong size/format, too many images), two languages or targets on the same store set, file too large, account/app id missing. Fix them or narrow the plan with `--target`/`--lang`.
- Skipped: languages without a store locale; Apple targets of the other platform (`APP_DESKTOP` is the macOS version, the others iOS – `store.apple.platform`).
- The confirm token is valid 30 minutes, once, and only for the project state of the plan: any saved change or changed image → "make a new plan".
- Apple: each set is made to hold exactly the planned images in order: screenshots already there with the same file content (checksum) are kept, everything else in the set is deleted, the missing images are uploaded, the order is set and verified; a missing localization or set is created. "Upload unchanged sets too" (`--force`) uploads every image again. Apple also wants the same language in the app information before submission (App Store Connect shows it).
- Apple processing: after the upload Apple processes every screenshot (usually seconds; in the first real run one image stayed in `UPLOAD_COMPLETE` for over 10 minutes). Vitrine Studio uploads all images of a set first, then waits for all of them together, up to 15 minutes per set. Images still processing after that are **not** an error: the set shows "Uploaded, Apple processing", the run finishes with "Apple is still processing N image(s)". They are in App Store Connect and are not uploaded again. Check later with "Check processing" (result) / "Check store state" (plan) / `vitrine upload plan --remote`: done → "Unchanged"; still processing → "Unchanged" with "Apple still processing N"; failed in the meantime → "Replace" (only the missing images are uploaded).
- Apple processing failed (`FAILED`, e.g. wrong dimensions): the set fails with Apple's message; the failed image is deleted; the next run uploads only that one.
- Progress per set in the GUI: "x.png: reserving…" → "uploading 45 %" → "committing…" → "Apple is processing 2 image(s) (UPLOAD_COMPLETE, 2:31)"; CLI prints the same on stderr. Cancel works at any time, also while waiting for Apple.
- A run never stays "running": a watchdog stops a run without any progress for 10 minutes (status failed, "no progress for …"); runs of an app that was closed or crashed during an upload show as "interrupted" the next time the upload log is opened (dialog, plan, `upload log`). Just plan and upload again.
- No editable App Store version (all versions released or in review): one message for the whole store – "No editable App Store version. Create a new version (e.g. 2.1.1) in App Store Connect, then plan again. Latest version: 2.1.0 (Ready for Distribution)." – with a button "Open App Store Connect" (the app's version page). The plan with "Check store state" shows it as a blocking step; in a run the Apple sets are "Skipped".
- Google: one edit for all languages; per language + type all images are deleted and re-uploaded in order, then committed. Any error or cancel discards the edit → nothing changes in Play. If Play refuses the commit asking for "changes not sent for review", run again with that option.
- Resume: just plan and upload again – sets that completed (same images) are skipped, failed/cancelled ones are uploaded again. A cancelled Apple set may be incomplete in App Store Connect until then.
- Rate limits: the run pauses ("Paused", up to 15 min) and retries; otherwise the set fails with "rate limited – try again later".
- Log: `<project>/.cache/uploads.sqlite` (runs, sets, files with store ids and status `done`/`processing`/`failed`, events with their real time: HTTP method, path, status – Apple's processing polls only as state changes – never keys or tokens). Not in Git (`.cache/`).
- AI assistants (MCP): `upload_plan` is free (dry run). `upload_execute {confirm_token}` needs the user's click "Confirm upload" in the Vitrine Studio window (dialog with the plan; declined or unanswered for 5 minutes → `not_confirmed`). Without the app (`vitrine mcp --headless`) assistant uploads are off unless the app setting `mcp_allow_headless_upload: true` is set in `settings.yaml`. Progress: `upload_status`, history: `upload_log`.

### Store upload – App Store upload method (App Asset Library, ADR 0019)
- Apple has two upload APIs: the **App Asset Library** (current, ASC API 4.5.1: images in a per-app library + "placements" on the version's languages) and the older **screenshot sets** (deprecated by Apple, still working). iPhone Duo screenshots and the new **header** and **search results** assets exist only in the asset library.
- Setting: project settings → Stores → App Store → "Upload method" = `store.apple.upload_flow` in `project.yaml`: `auto` (default, not written: the screenshot sets for every device they support – the method verified in a real upload – and the asset library only for iPhone Duo, header and search results targets), `asset_library` (opt-in, for trying it: everything through the library; plan blocked `asset_library_unavailable` if it is not available), `screenshot_sets` (only the older API). Duo/header/search targets never go into a screenshot set: without the library (setting, or no library access for this app/key) they are **skipped** with the warning `needs_asset_library`; the other sets still upload.
- The plan shows the method per store ("App Asset Library" / "Screenshot sets (older API)", CLI `flow …, setting …`), a set going the other way shows its own method (under `auto`: Duo/header/search "App Asset Library"), and why the library could not be used (`flow_note`). Library sets show where they go: locally `APP_SCREENSHOT · IPHONE_DUO`, with "Check store state" the real group `APP_SCREENSHOT → IPHONE_…_PROFILE`. With `asset_library`, a device App Store Connect does not list goes through the screenshot sets (note `flow_fallback`).
- Header / search results targets (presets `ios-header`, `ios-search-results`, `ios-creative-universal`): `store: {apple: {display_type: PRODUCT_PAGE_HEADER_ASSET, placement: header}}` (or `APP_STORE_SEARCH_RESULTS_ASSET` + `search_results`, or `PRODUCT_PAGE_HEADER_ASSET` + `universal` = one 16:9 image placed as both). They and `APP_IPHONE_DUO` never go into a screenshot set. Sizes (Apple, 2026-11-10): header 3840×1646 (21:9) or universal 5244×2950 PNG; search results 3:2, 1920×1280 to 3840×2560. Shown on iOS/iPadOS 27+ only; one header per placement group; the placement goes to every iPhone/iPad group App Store Connect lists for it.
- How the asset library upload works: images Vitrine Studio uploaded are named `<file> [<12 hex>]` in App Store Connect (a content fingerprint – the library has no checksums); an image the language already shows or the library already holds is reused, not uploaded again (also across languages with identical images). Old placements are removed, the new ones created and ordered; old images Vitrine Studio uploaded are deleted from the library after their placements (images still used by another language or uploaded by hand stay). If Apple fails to process an image, nothing on the store page changes; the next run uploads only that image.
- Checking the real App Store asset types (one-time, with your key): upload dialog → "Show App Store asset types", or `vitrine upload refdata [--account ID] [--app APPLE_ID|BUNDLE_ID] [--format json]` (works without a project; default account/app = the project's). Read-only. Lists Apple's placement types, groups (platform, display class), display classes, image sizes, whether the app can use the asset library, and how each Vitrine Studio slot resolves ("no group" = that device would fall back to screenshot sets). Mapping file: `crates/core/data/asset-library.yaml`.

### Templates (Phase 6.3, ADR 0023)
- A template = one or more canvases (e.g. Phone + Tablet + feature graphic) with their targets and variants, the styles, the texts in every language, images and fonts – a `.vitrine-template` file (zip). Licence always **CC0** (public domain); fonts inside keep the OFL.
- Built in: `phone` (3 pages; iPhone 6.9″, Google Play, blog banner, default) and `minimal` (1 page, iPhone). Your own (saved, imported, downloaded) live app-wide in `<app data>/templates/<id>/` (`VITRINE_APP_DIR` overrides the app folder).
- **New project from a template**: start screen → New project → pick a card (or "Import file…"); CLI `vitrine new <dir> --template <name|id|file> [--lang …]` (= `vitrine template new`). All canvases come along. Texts: per chosen language the same language, else its base language (`de-AT` ← `de`), else the template's default language (reported "copied, to translate"). Screenshots stay **empty** – the template's placeholders are not copied, so validation keeps asking for real screenshots and no placeholder can end up in the store.
- **Save as template**: canvases dialog → a canvas → "Save as template…" (choose canvases, name, id, description, author, tags, optionally also a file); CLI `vitrine --project P template save --name N [--canvas ID]… [--tag T]… [--id] [--version] [--replace] [-o file]`; MCP `template_save`. Same id again = replace (GUI asks implicitly, CLI needs `--replace`).
  - What goes in: the canvases + the targets showing them + variants, all styles, only the text keys the canvases use, images they use (files outside `assets/` are moved to `assets/`), fonts of the project's `fonts/` folder whose family a style names. Left out: store settings (`store:`), import mappings, your screenshots (replaced by generated placeholder screens in the device's aspect), imported vendor frames (previews always use the built-in drawn frames).
  - Fonts: only fonts that say "Open Font License" in their name table (licence description / URL) may go into a template; others are refused with "may not be redistributed" or "licence unclear (the font states no licence)". The licence file is kept if the project has one next to the font (`<name>-OFL.txt`, `<name>.txt`, `OFL.txt`, `LICENSE.txt`) else generated: copyright line from the font (+ Reserved Font Name) and the OFL 1.1 text → `fonts/<name>-OFL.txt`. Bundled Inter needs nothing. A font family a style names but the project lacks is reported ("the template uses Inter instead").
- **Insert from template** into the open project: canvases dialog → "+ New canvas" → "From template" (pick template, canvases, rule for equal style names; the dialog shows what will happen); CLI `vitrine --project P template insert <template> [--canvas ID]… [--styles rename|use-project] [--dry-run]`; MCP `template_insert` (`dry_run`). One undo step. Rules:
  - canvas/target ids already used get `-2` (`ios-iphone-69` → `ios-iphone-69-2`), element ids the next free number (`title-1` → `title-2`);
  - styles (colours, shadows, span styles, text styles): new names are added, equal definitions shared, a name the project defines differently is renamed in the inserted canvases (`accent` → `accent-2`, default "Keep both") or the project's definition is used ("Use this project's"); a renamed colour also renames the styles using it; the project's frame style stays;
  - texts: a key the project already has with the same texts is shared, else it becomes `<template id>.<key>`; languages mapped as for a new project (only the project's languages);
  - images/fonts are copied; identical files are reused, different ones with the same name get `-2`.
- Other commands: `vitrine template list [--format json]`, `import <file> [--replace]`, `export <id> -o <file>` (renders previews if missing; for sharing / the gallery), `remove <id>` (built-ins cannot be removed or replaced).
- Safe import (any file, also the gallery's): max 50 MB packed / 150 MB unpacked / 25 MB per file / 500 files; only `template.yaml`, `project.yaml`, `i18n/*.yaml`, `screenshots/…png|jpg`, `assets/…png|jpg|svg`, `fonts/*.ttf|otf` + `*.txt`, `previews/*.png`, checked by content; no `..`, absolute paths, hidden files or symlinks; SVG without scripts or external links; the project must load and validate (store-rule, screenshot and text-fit findings are tolerated).
- Gallery (`api.vitrinestudio.app`): backend skeleton in `crates/gallery-server` (not deployed yet; API `docs/gallery/API.md`, deployment/GDPR `docs/gallery/DEPLOY.md`). The server re-checks every upload, replaces all screenshots by its own placeholders and renders the previews itself. No "browse gallery" in the app yet.

- macOS menu bar (ADR 0020): the app menu's entries also sit in the system menu bar – Vitrine Studio menu (About, App settings… ⌘,, Services, Hide, Quit), File / Ablage (New ⌘N, Open ⌘O, Project settings, Targets, Export ⌘E, Upload, Import screenshots, Close project; project items greyed out without a project), Edit (Undo ⌘Z / Redo ⇧⌘Z = project history, or the text field's own undo while typing; Cut/Copy/Paste/Select All), Window, Help (store API key docs). Labels follow the UI language. Windows/Linux: only the in-app menu (☰ in the top bar).
- No browser context menu (Reload / Inspect Element) on right-click; text fields and selected text keep theirs (copy/paste, spelling). Developers: ⌥/Alt + right-click shows the web view's menu anywhere ("Inspect Element" in debug builds).
